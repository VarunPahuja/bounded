# Hash-chained audit ledger

Every record commits to the one before it. Change any byte of any past record and every hash after it stops matching, so tampering becomes detectable in a single linear pass.

Say what this is honestly: **tamper-evident, not tamper-proof.** Anyone with write access to the database can rewrite the whole chain from the point of edit forward. What closes that gap is anchoring the head hash somewhere they do not control. Section "Anchoring" below. Claiming immutability without anchoring is the mistake reviewers catch.

## Record shape

```
seq         BIGINT   monotonic, starts at 0, no gaps
ts          TIMESTAMPTZ  UTC, generated by the DB
actor       TEXT     who or what caused this
event_type  TEXT     enum from your reason-code set
payload     JSONB    the event body
prev_hash   CHAR(64) hash of seq-1, genesis uses 64 zeros
hash        CHAR(64) sha256 over everything above
```

`hash` is never part of `payload`. A record cannot commit to its own hash.

## Canonical serialisation

Two processes must produce byte-identical input for the same logical record, forever, across Python versions. That means one canonical form, decided once.

```python
# app/audit/hashing.py
import hashlib, json

GENESIS_PREV = "0" * 64
SEP = b"\x1f"          # unit separator, keeps field boundaries unambiguous


def canonical(payload: dict) -> bytes:
    return json.dumps(
        payload,
        sort_keys=True,
        separators=(",", ":"),
        ensure_ascii=False,
        allow_nan=False,
    ).encode("utf-8")


def record_hash(*, seq: int, prev_hash: str, ts: str, actor: str,
                event_type: str, payload: dict) -> str:
    h = hashlib.sha256()
    for field in (str(seq), prev_hash, ts, actor, event_type):
        h.update(field.encode("utf-8"))
        h.update(SEP)
    h.update(canonical(payload))
    return h.hexdigest()
```

Rules that keep this stable:

- **Separator between fields.** Without it, `actor="ab", type="c"` and `actor="a", type="bc"` hash identically. Cheap fix, real vulnerability.
- **Money as integers.** Paise, cents, never `Decimal` or float in the payload. `0.1 + 0.2` is not a hash input you want.
- **Timestamps as a fixed string.** Format once, hash the string you stored. `2026-09-15T10:04:00.123456Z`, always UTC, always microseconds. Re-formatting a `datetime` at verification time and getting a different precision is the classic false-positive.
- **`allow_nan=False`.** `NaN` is not valid JSON and round-trips inconsistently.
- **No key deletion.** Removing a key from a payload schema changes old hashes if you ever re-serialise from a typed model. Verify from the stored JSON text, not from a reconstructed object.

## Schema

```sql
CREATE TABLE audit_ledger (
    seq         BIGINT PRIMARY KEY,
    ts          TIMESTAMPTZ  NOT NULL,
    actor       TEXT         NOT NULL,
    event_type  TEXT         NOT NULL,
    payload     JSONB        NOT NULL,
    prev_hash   CHAR(64)     NOT NULL,
    hash        CHAR(64)     NOT NULL UNIQUE
);

CREATE INDEX audit_ledger_ts_idx ON audit_ledger (ts);
CREATE INDEX audit_ledger_type_idx ON audit_ledger (event_type);

CREATE OR REPLACE FUNCTION audit_ledger_append_only() RETURNS trigger AS $$
BEGIN
    RAISE EXCEPTION 'audit_ledger is append-only (attempted %)', TG_OP;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_ledger_no_mutate
    BEFORE UPDATE OR DELETE ON audit_ledger
    FOR EACH ROW EXECUTE FUNCTION audit_ledger_append_only();
```

The trigger stops application bugs and careless `UPDATE`s. It does not stop someone who can `ALTER TABLE ... DISABLE TRIGGER`. That is fine, the hash chain covers that case. Layered, not redundant.

Additionally revoke what you can: `REVOKE UPDATE, DELETE ON audit_ledger FROM app_user;` and let the app connect as a role that only has `INSERT` and `SELECT`.

## Appending under concurrency

Two concurrent appends both read the tip, both compute `seq = n+1`, one loses. The primary key saves you from corruption but you still need a retry or a lock. Take the lock, it is simpler to reason about.

```python
# app/audit/ledger.py
from datetime import datetime, timezone
from sqlalchemy import text
from .hashing import record_hash, GENESIS_PREV

LOCK_KEY = 0x4155444954         # any stable 64-bit constant


def append(session, *, actor: str, event_type: str, payload: dict) -> dict:
    session.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": LOCK_KEY})

    tip = session.execute(text(
        "SELECT seq, hash FROM audit_ledger ORDER BY seq DESC LIMIT 1"
    )).first()

    seq = 0 if tip is None else tip.seq + 1
    prev_hash = GENESIS_PREV if tip is None else tip.hash
    ts = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%S.%fZ")

    h = record_hash(seq=seq, prev_hash=prev_hash, ts=ts, actor=actor,
                    event_type=event_type, payload=payload)

    session.execute(text("""
        INSERT INTO audit_ledger (seq, ts, actor, event_type, payload, prev_hash, hash)
        VALUES (:seq, :ts, :actor, :et, CAST(:payload AS JSONB), :prev, :hash)
    """), {"seq": seq, "ts": ts, "actor": actor, "et": event_type,
           "payload": canonical(payload).decode(), "prev": prev_hash, "hash": h})

    return {"seq": seq, "hash": h, "ts": ts}
```

`pg_advisory_xact_lock` releases automatically at commit or rollback, so a crashed request cannot wedge the ledger. The lock serialises appends only, it does not touch reads.

Insert the **canonical text** you hashed. Letting the driver re-serialise a dict into JSONB is how you end up with a payload that does not reproduce its own hash.

## Verification

```python
def verify(session, batch: int = 1000) -> dict:
    prev_hash, expected_seq, checked = GENESIS_PREV, 0, 0
    while True:
        rows = session.execute(text("""
            SELECT seq, ts, actor, event_type, payload::text AS payload_text,
                   prev_hash, hash
            FROM audit_ledger WHERE seq >= :start ORDER BY seq LIMIT :n
        """), {"start": expected_seq, "n": batch}).all()
        if not rows:
            break
        for r in rows:
            if r.seq != expected_seq:
                return _fail("gap", expected_seq, r.seq)
            if r.prev_hash != prev_hash:
                return _fail("broken_link", r.seq)
            recomputed = record_hash(
                seq=r.seq, prev_hash=r.prev_hash, ts=r.ts, actor=r.actor,
                event_type=r.event_type, payload=json.loads(r.payload_text))
            if recomputed != r.hash:
                return _fail("hash_mismatch", r.seq)
            prev_hash, expected_seq, checked = r.hash, r.seq + 1, checked + 1
    return {"ok": True, "records": checked, "head": prev_hash}


def _fail(reason, seq, found=None):
    return {"ok": False, "reason": reason, "at_seq": seq, "found": found}
```

Distinguish the three failure modes in the output. They mean different things:

- `hash_mismatch` at seq N: record N was edited in place
- `broken_link` at seq N: record N-1 was edited or replaced
- `gap` at seq N: a record was deleted

Run verification on startup (cheap under ~100k rows), on demand from an admin endpoint, and in CI against a seeded fixture.

## Anchoring

Without this, an attacker with write access rewrites the chain end to end and verification passes. Publish the head hash somewhere outside the database:

- Log it at every append, to a log sink the app cannot rewrite
- Write a daily `checkpoints/YYYY-MM-DD.txt` containing `seq,head_hash` and commit it to git
- Print it on the dashboard so screenshots carry it
- For anything serious, a second system or an external timestamping service

Verification then becomes: chain is internally consistent **and** the head at checkpoint C matches what was published at time C. That is the claim you can actually defend.

## The tamper demo

Worth building explicitly, it is the most persuasive thirty seconds of any demo of this.

```python
# scripts/tamper_demo.py
append(s, actor="human:varun", event_type="AUTONOMY_RAISED",
       payload={"from": 500, "to": 1000})
print(verify(s))          # {'ok': True, ...}

s.execute(text("ALTER TABLE audit_ledger DISABLE TRIGGER audit_ledger_no_mutate"))
s.execute(text("UPDATE audit_ledger SET payload = jsonb_set(payload, '{to}', '5000') "
               "WHERE seq = 1"))
s.execute(text("ALTER TABLE audit_ledger ENABLE TRIGGER audit_ledger_no_mutate"))

print(verify(s))          # {'ok': False, 'reason': 'hash_mismatch', 'at_seq': 1}
```

Show the record that lies, show the seq where the chain breaks, show that nothing after seq 1 can be trusted either.

## When not to reach for a Merkle tree

Merkle trees buy you two things: O(log n) inclusion proofs for a third party, and efficient consistency proofs between two published heads. If nobody is requesting proofs and your ledger is under a few million rows, a linear chain with periodic checkpoints gives the same tamper evidence with a tenth of the code.

Add the tree when you have a concrete consumer for the proofs. Write down that decision as an ADR so the next reviewer does not re-litigate it.

## Failure modes to test

- [ ] Append 1000 records concurrently from 8 workers, verify passes, no gaps
- [ ] Edit a payload directly, verify reports `hash_mismatch` at the right seq
- [ ] Delete a record, verify reports `gap`
- [ ] Insert a record with a fabricated `prev_hash`, verify reports `broken_link`
- [ ] Unicode payload round-trips (`ensure_ascii=False` is doing work here)
- [ ] Payload with nested dicts in different insertion orders hashes identically
- [ ] Verify on an empty ledger returns ok with the genesis head
- [ ] `UPDATE` on the table raises, as does `DELETE`
